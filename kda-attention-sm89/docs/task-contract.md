# Task Contract

- Task name: kda-attention-sm89
- Objective: Implement a fused CUDA kernel (CuTe-DSL or plain CUDA C++, whichever is less risky per-step) for the Kimi Delta Attention (KDA) forward pass on compute capability 8.9 (RTX 4070 SUPER, Ada), using the chunkwise DPLR (diagonal-plus-low-rank) parallel algorithm, as a scoped-down, sm_89-compatible stand-in for the real NVIDIA KDA blog's FlashKDA kernel (which targets B300/Blackwell and cannot run on this GPU).
- Reference algorithm: `~/kimi-delta-attention` (cloned from github.com/hwilner/kimi-delta-attention, MIT-licensed educational implementation of arXiv:2510.26692).
  - Ground-truth oracle: `kda.core.KDACore` -- naive O(L) sequential recurrence, S_t = (I - beta_t k_t k_t^T) Diag(alpha_t) S_{t-1} + beta_t k_t v_t^T, o_t = S_t^T q_t.
  - Parallel reference (what the kernel should implement): `kda.chunkwise.chunkwise_dplr_forward` -- chunked WY-representation form (per-chunk coupling matmul, one C x C unit-lower-triangular solve, intra-chunk output matmul, inter-chunk state handoff). The repo's own test suite (23 tests, `tests/test_kda_core.py` + `tests/test_chunkwise.py`) already confirms this matches KDACore to float32 associativity error (~1e-6) -- verified passing on this machine before starting kernel work.
- Correctness requirements: kernel output matches `chunkwise_dplr_forward` (equivalently `KDACore`) within rtol=2e-2, atol=2e-2 (linear attention recurrences accumulate more float error than a single GEMM, hence looser tolerance than the GEMM task), across multiple random seeds, for a fixed representative config: head_dim=128, value_dim=128, chunk_size=64, batch_size=2, num_heads=4, seq_len in {512, 2048, 8192}.
- Performance or quality target: beat the pure-PyTorch-eager `chunkwise_dplr_forward` baseline (run on this GPU) on end-to-end latency at seq_len=8192 by a measurable margin (no fixed percentage target set upfront -- record whatever the first working fused kernel achieves, since there is no existing fused-kernel baseline on this GPU to calibrate a target against; revisit once the first number exists, mirroring how the GEMM task's atom_layout_mnk tuning only had its target set after candidate_001 existed).
- Allowed implementation approaches: Python host-side orchestration (one call per sequence; may loop over chunks on the host or do the inter-chunk loop inside a single persistent kernel -- implementer's choice per candidate) + CUDA C++ or CuTe-DSL device code, compiled for sm_89 only. No TMA, no tcgen05. PyTorch allowed for the reference/oracle and for tensor setup, not for the timed implementation path.
- Validation command: python validate.py
- Evaluation command: python benchmark.py
- Promotion criteria: candidate passes validate.py for all seq_len/seeds in the matrix AND benchmark.py shows a measured speedup over the PyTorch-eager chunkwise baseline at seq_len=8192, with the comparison numbers (not just a pass/fail) recorded as evidence.
